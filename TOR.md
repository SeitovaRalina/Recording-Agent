# Задача по агенту для записей интерью

Нужно разработать агента, который автоматизирует перенос записей интервью из Яндекс.Диска в Synology и прикрепляет финальную ссылку на запись в карточку интервью/кандидата в Notion.

Агент должен работать не как жесткий алгоритм, а как ассистент: если он не может однозначно выполнить действие, он должен обратиться к рекрутеру, описать проблему и принять уточнение в свободной форме.

### 1. Основной сценарий работы

1. Рекрутер проводит интервью в Яндекс.Телемосте.
2. Запись встречи сохраняется на Яндекс.Диск организатора встречи.
3. Агент по расписанию проверяет Яндекс.Диск на наличие новых записей. Также должна быть возможность ручной инициализации проверки, если запись нужно срочно перенести для общего доступа.
4. Агент находит новую необработанную запись.
5. Агент получает доступные метаданные записи:
    - дата и время создания;
    - название файла;
    - организатор/аккаунт владельца;
    - ссылка на файл;
    - возможные дополнительные метаданные, если доступны.
6. Агент ищет соответствующее событие в Яндекс.Календаре.
7. Агент анализирует событие календаря:
    - имя кандидата;
    - ссылку на подключение к встрече;
    - дату и время;
    - организатора;
    - дополнительные данные, если они есть.
8. Агент определяет, с какой Notion-базой нужно работать, исходя из того, кто проводил собеседование.
9. Агент пытается найти подходящую карточку интервью/кандидата в Notion.
10. Если карточка найдена однозначно, агент загружает запись в нужную папку Synology.
11. Агент создает ссылку на файл в Synology.
12. Агент добавляет или обновляет ссылку на запись в карточке Notion.
13. После успешной обработки агент удаляет или архивирует исходную запись на Яндекс.Диске.
14. Агент сохраняет статус обработки.
15. Если на каком-то этапе возникает неоднозначность или ошибка, агент обращается к рекрутеру через Mattermost и ожидает уточнение.

### 2. Источник записей

Основной источник для MVP — Яндекс.Диск.

Zoom в MVP не рассматривается как основной источник, так как компания официально ушла с Zoom. Если отдельные Zoom-записи все же появятся, они также должны попадать в рабочее пространство/диск аккаунта, а не храниться локально на ПК.

Локальный агент на компьютере рекрутера для MVP не требуется.

### 3. Расписание проверки

Агент не должен постоянно нагружать системы. Проверка должна выполняться по ограниченному расписанию.

Базовый вариант для MVP:

- автоматическая проверка 1 раз в сутки;
- ручной запуск проверки по команде из Mattermost;
- возможно, дополнительная проверка несколько раз в день, если это понадобится процессу.

Примеры команд:

```
/recordings check
/recordings pending
/recordings status
```

### 4. Разделение записей интервью и обычных командных встреч

Агент должен отличать записи собеседований от других встреч.

Для этого можно использовать несколько признаков:

1. Владелец записи — рекрутер.
2. Запись создана в рабочем календаре рекрутера.
3. Рядом по времени есть событие в Яндекс.Календаре, созданное через calink.ru.
4. В событии есть ссылка на Яндекс.Телемост.
5. В событии есть имя кандидата.
6. В событии/названии есть признаки интервью.
7. Запись находится в определенной папке Яндекс.Диска, если такая структура будет настроена.

Если агент не уверен, что запись относится к интервью, он должен не обрабатывать ее автоматически, а отправить ее в статус “требуется проверка”.

### 5. Матчинг записи с событием календаря

Так как записи сами по себе могут иметь технические названия и не содержать данных кандидата, агент должен использовать Яндекс.Календарь.

Сопоставление должно выполняться по нескольким признакам:

- дата и время записи;
- организатор/рекрутер;
- ссылка на встречу;
- имя кандидата из события;
- длительность встречи, если доступна;
- дополнительные данные события, если доступны.

Гарантированно в событии календаря есть:

- имя кандидата;
- ссылка на подключение к встрече.

Не гарантировано:

- email кандидата;
- фамилия;
- совпадение почты с Notion;
- прямой идентификатор карточки Notion.

Если событие календаря не найдено или найдено неоднозначно, агент должен обратиться к рекрутеру.

### 6. Работа с Notion

В Notion есть несколько баз данных, и структура зависит от рекрутера.

Для MVP нужно поддержать раздельную работу с базами:

- база Антона;
- база Лили;
- при необходимости другие базы в будущем.

Выбор базы должен зависеть от рекрутера/организатора интервью.

Для базы Interviews по инженерному рекрутингу важны поля:

- `Name` — имя и фамилия, тип: название сущности;
- `General Interview Date` — дата интервью, тип: дата;
- `General Interview recording` — ссылка на запись;
- `TBD` — контакты кандидата, формула на основе другой базы Candidates;
- relation-поля, например `Spots`, которые связывают интервью с конкретным проектом/ставкой.

Важно: в базе может быть несколько карточек с одинаковым именем. Это может означать как разных людей, так и одного кандидата, который рассматривается на разные проекты.

### 7. Логика поиска карточки Notion

Агент должен искать карточку по доступным признакам:

1. Имя кандидата из календаря.
2. Дата интервью.
3. Рекрутер/организатор.
4. Связанный проект/ставка, если это можно определить.
5. Контакты кандидата, если они доступны и могут быть распарсены.
6. Ссылка на встречу, если она где-то хранится в Notion.

Если найдена ровно одна уверенная карточка, агент может обновить ее автоматически.

Если найдено **несколько карточек с одинаковым именем** или есть сомнения, агент должен отправить рекрутеру запрос на ручное уточнение.

Пример:

```
Найдена запись интервью, но есть несколько подходящих карточек:

1. Василий Петькин — Android от Яндекс
2. Василий Петькин — Android от Сбер

Куда прикрепить запись?
Можно ответить свободным текстом, например:
“в карточку Сбера”
“в обе карточки”
“вот сюда: [ссылка на Notion]”
```

### 8. Взаимодействие через Mattermost

Агент должен уметь взаимодействовать с рекрутером через Mattermost.

Mattermost используется как интерфейс для:

- уведомлений об успешной обработке;
- уведомлений об ошибках;
- ручного сопоставления записи с карточкой;
- ручного запуска проверки;
- повторной обработки после ошибки;
- принятия свободного текстового ответа от рекрутера.

Агент должен понимать не только кнопки, но и обычные сообщения пользователя.

Пример сообщения:

```
⚠️ Требуется ручное сопоставление записи

Запись: Yandex Telemost meeting 2026-07-06 15-30 — recording.webm
Дата: 06.07.2026, 15:30
Рекрутер: anna@company.com
Событие календаря: Interview Backend Developer

Проблема:
Найдено несколько карточек с похожим именем.

Возможные карточки:
1. Иванов Иван — Backend / Project A
2. Иванов Иван — Backend / Project B

Можно ответить:
“прикрепи к Project A”
“прикрепи в обе”
“вставь ссылку вот сюда: [Notion URL]”
```

### 9. Synology

Synology используется как финальное хранилище записей.

Агент должен:

1. Определить целевую папку в Synology.
2. Загрузить туда файл записи.
3. Создать ссылку на файл.
4. Передать эту ссылку в Notion.

Правила выбора папки должны быть определены после получения структуры папок Synology. Эту структуру предлагается перенести/описать в Notion, чтобы агент мог использовать ее как источник правил.

### 10. Удаление исходной записи

После успешной обработки агент должен удалить исходную запись на Яндекс.Диске.

Успешной обработкой считается ситуация, когда:

1. Запись загружена в Synology.
2. Ссылка Synology создана.
3. Ссылка добавлена в нужную карточку Notion.
4. Статус обработки сохранен.

Если хотя бы один шаг завершился ошибкой, исходную запись удалять нельзя.

### 11. Статусы обработки и хранение данных

Агент должен сохранять статус каждой найденной записи в собственной технической базе данных. В качестве основной БД для агента планируется использовать **PostgreSQL**.

PostgreSQL будет использоваться как источник истины по обработке записей: какие файлы уже найдены, какие обработаны, какие требуют ручного уточнения, какие завершились ошибкой и какие действия были выполнены.

Возможные статусы обработки:

- `found` — запись найдена;
- `calendar_event_found` — найдено событие календаря;
- `candidate_matched` — карточка Notion определена;
- `manual_review_required` — требуется ручное уточнение;
- `transfer_started` — начата передача записи в Synology;
- `uploaded_to_synology` — запись загружена в Synology;
- `synology_link_created` — ссылка Synology создана;
- `notion_updated` — карточка Notion обновлена;
- `source_marked_processed` — исходная запись на Яндекс.Диске помечена как обработанная;
- `source_deleted` — исходная запись удалена с Яндекс.Диска, если это предусмотрено политикой хранения;
- `completed` — обработка завершена;
- `ignored` — запись помечена как не относящаяся к интервью;
- `failed` — обработка завершилась ошибкой.

В PostgreSQL должны храниться только технические данные и метаданные, необходимые для работы агента:

- ID записи в системе агента;
- ID файла на Яндекс.Диске;
- путь к файлу на Яндекс.Диске;
- название файла;
- дата и время создания записи;
- владелец файла / рекрутер;
- источник записи;
- найденное событие Яндекс.Календаря;
- ID события календаря;
- данные кандидата из календаря;
- выбранный Notion-профиль/адаптер;
- ID Notion-базы;
- ID выбранной карточки Notion;
- ссылка на карточку Notion;
- выбранная папка Synology;
- путь файла в Synology;
- созданная Synology-ссылка;
- текущий статус обработки;
- текст ошибки, если она возникла;
- история попыток обработки;
- ID треда/сообщения в Mattermost для manual review;
- время последней проверки;
- время успешной обработки;
- признак, что исходный файл уже обработан;
- срок, после которого исходную запись можно удалить, если будет использоваться retention policy.

Сами видеофайлы в PostgreSQL храниться не должны.

Передача файла из Яндекс.Диска в Synology должна по возможности выполняться потоково, без долговременного сохранения полного файла на сервере агента:

```
Яндекс.Диск
↓ потоковая передача
сервер агента
↓ потоковая передача
Synology
```

Если потоковая передача технически невозможна или потребуется fallback, допускается временное сохранение файла на сервере только на время конкретной задачи обработки. После успешной загрузки в Synology временный файл должен быть удален сразу.

При ошибке обработки временный файл не должен храниться постоянно. Для аварийных случаев можно предусмотреть короткий TTL хранения временных данных, например несколько часов, после чего они должны автоматически удаляться.

Таким образом:

- PostgreSQL хранит статусы, связи, идентификаторы и метаданные;
- Synology хранит финальные видеофайлы;
- Notion хранит ссылку на запись в Synology;
- Mattermost используется для коммуникации с рекрутером;
- сервер агента не является файловым хранилищем.

### 12. Тестовое окружение

Для разработки MVP нужно использовать тестовое окружение в виде полной копии всех систем:

- тестовая папка Яндекс.Диска;
- тестовый Яндекс.Календарь;
- тестовая/скопированная Notion-база;
- тестовая папка Synology;
- тестовый Mattermost-канал или бот.

После проверки агент можно перенести на реальную структуру, выдав ему production-доступы.
