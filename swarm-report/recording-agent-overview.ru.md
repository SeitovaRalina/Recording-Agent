# Recording Agent: текущее состояние и тестирование

Актуально на 22 июля 2026 года.

## 1. Что это за система

Recording Agent автоматизирует обработку записей интервью:

```text
Яндекс.Диск
  -> поиск новой записи Телемоста
  -> сопоставление с событием Яндекс.Календаря
  -> поиск кандидата в Notion
  -> сохранение файла в хранилище
  -> добавление ссылки в Notion
  -> уведомление рекрутера
```

OpenClaw-агент (сначала Mila, позднее Sylvanas) отвечает только за общение с
пользователем на естественном языке. Backend остаётся владельцем расписания,
PostgreSQL-состояния, matching, загрузки файлов, обновления Notion и всех side effects.
Обычный детерминированный путь не требует отдельного LLM-вызова на каждом шаге.

## 2. Что уже сделано

- Реализован FastAPI Backend с PostgreSQL-состоянием и Alembic-миграциями.
- Реализованы ручной scan и код ежедневного scheduled scan. В локальном canary
  scheduler намеренно выключен.
- Реализован поиск записей в папке `/Записи Телемоста/` каждого настроенного
  рекрутера.
- Реализовано сопоставление записи с выбранными календарями рекрутера.
- Реализован поиск кандидата в Notion по имени и дате интервью.
- Реализованы детерминированное имя файла, storage key и защита от коллизий.
- Для canary используется отдельное тестовое хранилище MinIO и база Test Interviews.
- Реализован operator-only onboarding рекрутера с явным выбором Notion database,
  проверкой календаря и preflight перед активацией.
- Реализованы защищённые Backend intents: scan, status, review context, resolve и ignore.
- Реализованы one-time review token, TTL, привязка к recruiter/recording/review/version/thread,
  optimistic version check и idempotency/replay protection.
- Создан переносимый workspace skill `recording-agent` с детерминированным CLI.
- Ответы scan/status показывают количество и список записей, итоговый статус,
  необходимость review, безопасную причину review, recording ID, имя файла и ссылку,
  если они доступны.
- Для внутреннего Codex-теста Mattermost-доставка отключается. Trusted recruiter ID
  приходит из process environment и не запрашивается у пользователя в чате.
- Локальные quality gates пройдены: `ruff`, `mypy`, skill validation и полный
  `pytest` (`190 passed, 1 warning`). Warning относится только к невозможности Windows
  создать `.pytest_cache`.

На Mila пока выполнен только read-only discovery окружения. Skill и Backend на Mila
ещё не развёрнуты, production-данные не изменялись.

После проверки локального canary Антон подтвердил обновлённый целевой сценарий. Он ещё не
реализован полностью: текущий Backend всё ещё использует дату как часть Notion lookup и thread
binding для review. Эти расхождения перечислены ниже и добавлены в Phase 4 plan как утверждённая
поправка, а не как уже готовый функционал.

## 3. Что умеет агент

Пользователь может писать свободным русским или английским текстом.

### Запустить проверку

Пример:

> Проверь новые записи собеседований.

Агент запускает один Backend scan и возвращает:

- сколько файлов обнаружено;
- сколько новых записей добавлено;
- сколько старых файлов пропущено canary-фильтром;
- какие записи обработаны без review;
- какие требуют review и почему;
- какие завершились ошибкой.

### Получить статусы

Поддерживаются фильтры по дате, кандидату, recording ID и статусу.

Примеры:

> Покажи статусы записей за сегодня.

> Найди записи кандидата Артем Зайцев.

> Покажи запись с recording ID `<UUID>`.

> Покажи только записи, которые требуют review.

### Разрешить неоднозначность

В целевом Mila-flow отдельные Mattermost threads не используются. Mila работает в обычном личном
чате и сначала отправляет одну сводку по всем записям, а затем — пронумерованные вопросы с
конкретным действием, необходимым для завершения каждой записи. Пользователь может ответить на
все вопросы сразу или только на часть свободным текстом.

Mila сообщает, как поняла ответ, пишет о начале обработки и затем присылает результат или ошибку.
Неотвеченные вопросы остаются в PostgreSQL и повторяются в следующей ежедневной сводке в 18:00 по
локальному времени рекрутера; закрытые вопросы не повторяются.
Если ответ можно связать с несколькими вопросами, Mila переспрашивает и ничего не изменяет.
Посторонние обращения к Mila по другим задачам не считаются ответами Recording Agent.

Backend проверяет пользователя, DM channel, recording/review, одноразовую capability, TTL и
текущую версию recording. Один ответ может продолжить обработку только один раз.

Название карточки Interviews не считается уникальным. Если найдено несколько карточек с одним
именем, Mila показывает для каждого варианта ссылку на страницу и различия карточек. Как минимум
показывается `📍 Spots`, потому что это могут быть разные люди с одинаковым именем или один кандидат,
которого рассматривают на разные проекты. Если Backend вернул другие безопасные отличия по
Candidate или проекту, они также показываются. Одинаковые title нельзя объединять или выводить как
несколько неразличимых ссылок.

В локальном Codex-тесте реальные Mattermost DM отключены. Здесь проверяются scan и status, а
текущий token/thread/replay contract покрыт автоматическими тестами. Новый обычный DM-flow,
частичные ответы и напоминания нужно реализовать и отдельно проверить на Mila.

### Сообщить результат

После подключения Mattermost Backend сможет проактивно отправлять completion/error DM.
Сейчас в Codex результат возвращается непосредственно в диалог с Codex.

## 4. Рекомендуемый формат календарного события

Для надёжного автоматического matching нужен единый формат.

Рекомендуемый title:

```text
Встреча на 30 минут (Имя Фамилия)
```

Допустим другой текст перед скобками, но имя кандидата должно находиться в круглых
скобках в самом конце title. Например:

```text
Общее интервью (Артем Зайцев)
```

Правила заполнения:

1. Title календарного события должен совпадать с title, который попадает в имя записи
   Телемоста. Backend нормализует регистр и пробелы, но не угадывает другой смысловой title.
2. Имя кандидата указывается в круглых скобках в конце title.
3. `General Interview Date` заранее не заполняется и не участвует в обязательном поиске карточки.
   После обработки Backend записывает туда дату сопоставленного события календаря.
4. `Name` в Notion должен содержать имя кандидата. Карточка ищется прежде всего по имени. Email
   можно использовать как дополнительный сигнал: контакты находятся в formula-поле `TBD`, которое
   возвращает смешанный текст с телефоном, email и Telegram. Backend извлекает только валидный
   email; отсутствие или несовпадение email не отменяет совпадение по имени.
5. Источник project/spot в test и production настраивается по точному API-имени
   `📍 Spots: relation`. Backend должен получить title ровно одной связанной Spot-страницы.
   Пустое значение даёт `unspecified`.
   Если relation заполнена одной страницей, `unspecified` является ошибкой. Правило для нескольких
   связанных `📍 Spots` ещё нужно согласовать.
6. Событие должно находиться в default/selected calendar рекрутера.
7. Время записи должно попадать в интервал события с допуском 15 минут до и после.
8. Ссылка Telemost подтверждает видеовстречу, а ссылка calink.ru в description является
   сильным признаком текущего booking-flow.
9. Не следует создавать два подходящих выбранных события с одинаковым title и временем:
   такая ситуация намеренно отправляется на manual review.

Если эти условия не выполнены, Backend не делает рискованный автоматический выбор, а возвращает
`manual_review_required` с конкретной причиной и вопросом: что именно должен выбрать или уточнить
сотрудник, чтобы завершить обработку.

## 5. Как сейчас работает ignore

В системе есть три разных механизма, которые важно не смешивать.

### 5.1 Пропуск старых файлов в canary

При `SCAN_IGNORE_BEFORE_TODAY=true` Backend видит файлы в `/Записи Телемоста/`, но не
добавляет в PostgreSQL файлы, созданные до начала текущего дня в настроенной локальной
таймзоне. Они учитываются в результате как `skipped_legacy`.

Это временная защита canary от массового подхвата исторического архива. Она не ставит
метки на Яндекс.Диске и ничего не удаляет. После сброса локальных данных повторный scan
снова возьмёт сегодняшние файлы, а старые снова пропустит.

### 5.2 Ручной ignore конкретной записи

Если запись неоднозначна, рекрутер может явно выбрать «оставить без обработки». Backend переводит
её в терминальный статус `ignored`. Файл на Яндекс.Диске при этом не удаляется и не изменяется.
Следующий scan узнаёт запись по устойчивому Yandex file ID и не создаёт новый recording.

Если пользователь объясняет, что это не интервью, но просит сохранить рабочую встречу в
конкретную папку Synology, это отдельный сценарий, а не `ignored`: Backend загружает файл в
разрешённое место, возвращает ссылку и завершает запись без обновления карточки кандидата.
Пользователь может выбрать существующую папку или попросить создать новую. Backend создаёт её
только внутри настроенного корня рекрутера после проверки пути и прав.

Автоматический ignore неоднозначных событий запрещён: требуется явное решение рекрутера.

### 5.3 Метка processed

В production-коде предусмотрена Yandex custom property `processed=true`, чтобы уже успешно
перенесённый файл не обрабатывался повторно. В текущем canary
`YANDEX_SOURCE_MUTATION_ENABLED=false`, поэтому Backend не ставит эту метку.

## 6. Удаление старых записей из Яндекс.Диска

В коде существует прежняя двухэтапная retention-модель:

1. после успешного переноса поставить `processed=true`;
2. не раньше чем через 7 дней переместить processed-файл в Trash;
3. permanent purge никогда не запускается по расписанию и требует отдельного свежего
   operator approval.

В canary вся Yandex mutation, cleanup и permanent purge жёстко выключены.

Уточнено, что сама папка `/Записи Телемоста/` автоматически очищается Яндексом через 90 дней и не
расходует обычную квоту облачного хранилища. Поэтому автоматическое удаление со стороны Recording
Agent не требуется.

По просьбе Антона должна остаться ручная команда «почисти успешно обработанные записи». Сначала
Backend показывает ограниченный preview и просит явное подтверждение. После подтверждения он может
переместить в Trash только файлы, для которых Backend доказал успешное завершение и наличие ссылки
в конечном хранилище. Failed, review, незавершённые и непроверенные записи не включаются.
Permanent purge через Mila недоступен. Минимального возраста нет: файл можно включить в preview
сразу после доказанного успешного завершения. Явное подтверждение всё равно обязательно.

Retention записей в PostgreSQL и Synology — отдельные политики, они не определяются
автоматической очисткой Яндекс.Диска.

## 7. Как протестировать сейчас на Codex

Полная инструкция находится в
[`phase-4-codex-agent-test-runbook.ru.md`](phase-4-codex-agent-test-runbook.ru.md).

Короткий сценарий:

1. Запустить Docker Desktop.
2. Из корня репозитория поднять локальный Backend, PostgreSQL и MinIO:

   ```powershell
   docker compose up --build -d --wait
   docker compose ps
   Invoke-RestMethod http://127.0.0.1:18000/health
   ```

3. Загрузить Backend URL, secret и trusted recruiter ID в process environment по разделу
   10 полного runbook. Не печатать значения secret/token.
4. Запустить новую Codex-сессию из корня репозитория. Уже открытая сессия не получает
   новые environment variables.
5. Написать:

   > Проверь новые записи собеседований.

6. Проверить повторный запрос:

   > Проверь ещё раз новые записи собеседований.

   Повтор не должен создать дубликаты или повторные side effects.
7. Проверить status:

   > Покажи статусы записей за сегодня.

   > Покажи только записи, которые требуют review.

8. Проверить ответы по кандидату и recording ID.
9. Не выполнять `docker compose down -v`: named volumes используются для проверки
   restart recovery.

Локальное recording state сейчас очищено и готово к повторному scan. При действующем
canary cutoff старые файлы будут показаны как skipped, а сегодняшние — обработаны заново.
