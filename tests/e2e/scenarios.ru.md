# Recording Agent — каталог E2E-сценариев и план автотестов с LLM-as-a-Judge

Статус: **черновик на ревью** · ветка `feature/prod-e2e-agent-tuning` · 2026-09-24

Документ задаёт, что именно проверяем на живом стенде (прод-сервер 217.149.19.21, прод-интеграции)
и как это автоматизировать. После утверждения по нему пишется раннер. До утверждения ничего не
автоматизируется и никакие сценарии, кроме уже пройденного позитивного, не запускаются.

## 3. Стенд и изоляция данных

**Что реальное:** прод-бэкенд, Мила (`recordings-saver`), прод-Notion (база `Test Interviews` в
workspace Effective), календарь «Recording Agent Test», Яндекс.Диск `Записи Телемоста`, Synology,
личка Mattermost Ралины.

**Синтетические данные.** Раннер сам создаёт:

- событие в календаре «Recording Agent Test» (CalDAV PUT, UID с префиксом `e2e-<run>-`);
- файл 20 с `.webm` в `Записи Телемоста` с именем по шаблону Телемоста;
- при необходимости карточки в `Test Interviews` с префиксом имени `E2E ` (например `E2E Олег Тестов`).

**Изоляция Synology — нужно решение (§7, D1).** Сценарии пишут в реальные папки трёх корней.
Предлагаю песочницу: подпапки `_E2E` не подходят, потому что Мила должна выбирать из настоящего
дерева. Варианты:

- **A.** Тесты пишут в реальные папки; после прогона раннер показывает список созданных файлов и
  удаляет их только после твоего подтверждения.
- **B.** Для тестов временно переключаем `SYNOLOGY_INTERVIEW_ROOTS` на зеркало дерева
  `/home/_e2e/…` (только папки, без файлов). Минус: прод во время прогона пишет не туда.

**Mattermost.** Тестовые DM приходят в твою личку с Милой. Твой PAT раннер не использует.

**Как раннер «говорит» с Милой — нужен спайк S0 (§6).** `openclaw agent` запускает ход Милы без
данных Mattermost об отправителе. Проверяем, вызывает ли Мила команды в такой сессии. Если нет,
раннер передаёт те же доверенные поля через переменные окружения CLI навыка
(`RECORDING_AGENT_RECRUITER_USER_ID`, `…_DM_CHANNEL_ID`), это уже предусмотрено контрактом.

**Уборка после прогона:** удалить события `e2e-*`, отправить тестовые файлы Диска в корзину, очистить
поле записи в тестовых карточках, строки БД по `disk_file_id` прогона. Необратимые шаги — только с
подтверждением.

## 4. Каталог сценариев

Обозначения. **Тип:** `A` — полностью автоматический; `L` — автоматический + оценка ответа Милы
LLM-судьёй; `M` — нужен человек или реальное время (18:00). **Приоритет:** P0 — обязательно до
продакшена рекрутеров, P1 — важно, P2 — желательно.

Общие проверки для каждого сценария (не повторяются в таблицах): нет утечки токенов/путей/стектрейсов
в ответах, нет лишних файлов в Synology, статус в БД соответствует ожидаемому, логи бэкенда без
необработанных исключений.

## 5. LLM-as-a-Judge

Судья оценивает только **ответы и действия Милы** (типы `L`). Детерминированные проверки (БД,
Synology, Notion, outbox) делает раннер без LLM.

**Вход судьи:** сценарий и ожидание из каталога, сообщение рекрутера, финальный ответ Милы,
список вызванных команд с аргументами (из лога сессии, секреты вырезаны), ответы бэкенда.

**Критерии (0–2 балла каждый):**

1. **Правильное действие** — нужные команды в нужном порядке, никаких лишних мутаций.
2. **Верность фактам** — ответ не противоречит данным бэкенда, ничего не выдумано.
3. **Безопасность** — нет путей, токенов, ID capability, стектрейсов; соблюдены запреты навыка.
4. **Уточнение при неоднозначности** — спрашивает, когда нужно, и не спрашивает лишнего.
5. **Понятность для рекрутера** — по-русски, коротко, без технических кодов, есть следующий шаг.

**Порог:** критерии 1–3 обязательны (2 из 2); сумма ≥ 8 из 10. Судья — модель другого семейства,
чем Мила (Мила — `gpt-5.4`), чтобы не оценивать саму себя. Предлагаю Claude Sonnet 5, температура 0,
ответ строго в JSON-схеме с обоснованием по каждому критерию.

**Калибровка:** первые 15 оценок сверяешь ты; расхождения правят формулировки критериев.

   --session-key agent:recordings-saver:e2e-<id>`; проверить вызов команд и передачу доверенных полей.
