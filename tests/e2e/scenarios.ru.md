# Recording Agent — каталог E2E-сценариев и план автотестов с LLM-as-a-Judge

Статус: **на ревью, решения D1–D7 приняты** · ветка `feature/prod-e2e-agent-tuning` · 2026-09-24

Документ задаёт, что именно проверяем на живом стенде (прод-сервер 217.149.19.21, прод-интеграции)
и как это автоматизировать. После утверждения по нему пишется раннер. До утверждения ничего не
автоматизируется и никакие сценарии, кроме уже пройденного позитивного, не запускаются.

## 2. Как устроено тестирование

Каталог в разделе 4 — это **список того, что должно быть проверено**, а не порядок запуска.
Запускаем мы **сквозные маршруты**: каждый маршрут — одна история рекрутера от появления записи до
результата в Synology и Notion. Каждый пункт каталога попадает хотя бы в один маршрут или в быстрые
проверки уровня 2.

### Уровень 1. Сквозные маршруты с Милой

Один маршрут проходит так:

```text
1. Подготовка   событие в календаре + файл на Диске (+ карточка в Notion, если нужна)
2. Запуск       сообщение Миле («Проверь новые записи») или таймер / cron-воркер
3. Диалог       ответы рекрутера по сценарию — заранее написанные фразы, не импровизация
4. Проверка     после каждого ответа Милы: БД, Synology, Notion, очередь уведомлений
5. Оценка       LLM-судья оценивает каждый ответ Милы по критериям раздела 6
6. Уборка       тестовые события, файлы, поля в Notion, строки в БД
```

| Маршрут | История | Пункты каталога | Сообщений рекрутера (цель) |
|---|---|---|---|
| R01 | Один кандидат, папка однозначна | A1, B1, C1, D1/D3, F1, H2, I | **1** |
| R02 | Папка неоднозначна (`Flutter`) | A1, B1, C1, D2, D7, F1, H2 | 2 |
| R03 | Нет подходящей папки → новая | D4, D5, D6, F1 | 2 |
| R04 | Тёзки в Notion | C5, C6, F1 | 2 |
| R05 | Несколько спотов у карточки | C3, C4, F1 | 2 |
| R06 | Проблемы календаря | B2, B3, B5, C7 | 1–2 |
| R07 | Пачка из трёх записей, частичные ответы | G1–G5, G9, G10, H1 | 3 |
| R08 | Рабочая встреча и пропуск | J1–J3 | 1–2 |
| R09 | Ошибка и повтор | F5/N2 (ошибка создаётся искусственно), H3, повтор, F1 | 2 |
| R10 | Перенос и перепривязка | K1–K4 | 2–3 |
| R11 | Автомаршрутизация | E0–E10 | 0–1 |
| R12 | Очистка Диска | L1–L6 | 2 |
| R13 | Атаки и границы | M1–M5, I3, I4, E5 | — |
| R14 | Сводка по расписанию в заданное время `T` | G6, G8, O1–O3 (G7 — уровень 2) | 0 |
| R15 | Устойчивость | N1, N4–N6, F2–F4 | — |

**Число сообщений рекрутера — отдельная метрика.** Если Мила требует больше сообщений, чем в колонке
«цель», маршрут считается проваленным по UX, даже если запись в итоге сохранена.

### Уровень 2. Быстрые проверки без Милы

Пункты с детальной логикой бэкенда (B4–B11, A3–A7, F7, M1–M4 и т.п.) проверяются напрямую через API
бэкенда таблицей «вход → ожидаемый статус». Это быстро, дёшево и не расходует LLM. Уровень 2 идёт
первым: если он красный, маршруты уровня 1 не запускаются.

### Порядок прогона

1. Уровень 2 целиком.
2. R01 (дымовой). Если красный — стоп.
3. R02–R13, R15 по одному, с уборкой после каждого.
4. R14 — в заранее выбранное время `T` (см. ниже).
5. Сводный отчёт; отложенные дефекты → исправление → повтор затронутых маршрутов.

### R14: сводка в заданное время

Ждать 18:00 не нужно. Время сводки выносится из константы в настройку `SUMMARY_LOCAL_TIME`
(`HH:MM`, по умолчанию `18:00`, часовой пояс — рекрутера). Для прогона:

1. Выбираем `T` = ближайшее время + 15 минут, ставим в `backend.env`, перезапускаем backend.
2. Готовим 2 открытых вопроса и 1 вопрос по уже сохранённой записи (G8).
3. Проверяем: ровно одно сообщение в личку, пришло в интервале `[T; T+2 мин]` (диспетчер работает
   раз в минуту), формат соответствует шаблону сводки, вопрос по сохранённой записи в неё не попал,
   в `question_digests` одна строка за дату со статусом `sent`, повторного сообщения в `T+5 мин` нет.
4. Возвращаем `18:00` и перезапускаем backend.

Ограничение: сводка одна на локальную дату. Если R14 прошёл сегодня днём, в реальные 18:00 сегодня
её уже не будет — это ожидаемо. Повтор напоминания на следующий день и `suppressed` (G7) проверяются
на уровне 2 с подставленным временем, без ожидания суток.

### Отчёты

Каждый прогон — папка `tests/e2e/reports/<дата>_<N>/`, внутри по одному файлу на маршрут
(`R01.md` … `R15.md`, `level2.md`) и `summary.md`. Все файлы маршрутов — строго по шаблону
[`reports/TEMPLATE.md`](reports/TEMPLATE.md): одинаковые разделы в одинаковом порядке, чтобы прогоны
сравнивались между собой.

### Найденные ошибки во время прогона

| Класс | Примеры | Когда исправляем |
|---|---|---|
| **Блокер** | маршрут не доходит до конца; неверная папка/карточка; утечка секрета; порча данных | Сразу: стоп прогона → тест на ошибку → исправление → деплой → повтор этого маршрута и уже зелёных маршрутов, которые задевает правка |
| **Не блокер** | формулировка Милы, лишнее сообщение, низкая оценка судьи по понятности | После полного прогона, пачкой; повтор только затронутых маршрутов |

Каждый дефект записывается в отчёт маршрута (ID, класс, статус, коммит исправления), даже если
исправлен сразу.

## 4. Стенд и изоляция данных

**Что реальное:** прод-бэкенд, Мила (`recordings-saver`), прод-Notion (база `Test Interviews` в
workspace Effective), календарь «Recording Agent Test», Яндекс.Диск `Записи Телемоста`, Synology,
личка Mattermost Ралины.

**Синтетические данные.** Раннер сам создаёт:

- событие в календаре «Recording Agent Test» (CalDAV PUT, UID с префиксом `e2e-<run>-`);
- файл 20 с `.webm` в `Записи Телемоста` с именем по шаблону Телемоста;
- при необходимости карточки в `Test Interviews` с префиксом имени `E2E ` (например `E2E Олег Тестов`).

**Изоляция Synology — решено: реальные папки (§8, D1).** Сценарии пишут в реальные папки трёх корней.
Предлагаю песочницу: подпапки `_E2E` не подходят, потому что Мила должна выбирать из настоящего
дерева. Варианты:

- **A.** Тесты пишут в реальные папки; после прогона раннер показывает список созданных файлов и
  удаляет их только после твоего подтверждения.
- **B.** Для тестов временно переключаем `SYNOLOGY_INTERVIEW_ROOTS` на зеркало дерева
  `/home/_e2e/…` (только папки, без файлов). Минус: прод во время прогона пишет не туда.

**Mattermost.** Тестовые DM приходят в твою личку с Милой. Твой PAT раннер не использует.

**Как раннер «говорит» с Милой — нужен спайк S0 (§7).** `openclaw agent` запускает ход Милы без
данных Mattermost об отправителе. Проверяем, вызывает ли Мила команды в такой сессии. Если нет,
раннер передаёт те же доверенные поля через переменные окружения CLI навыка
(`RECORDING_AGENT_RECRUITER_USER_ID`, `…_DM_CHANNEL_ID`), это уже предусмотрено контрактом.

**Уборка после прогона:** удалить события `e2e-*`, отправить тестовые файлы Диска в корзину, очистить
поле записи в тестовых карточках, строки БД по `disk_file_id` прогона. Необратимые шаги — только с
подтверждением.

## 5. Каталог сценариев

Обозначения. **Тип:** `A` — полностью автоматический; `L` — автоматический + оценка ответа Милы
LLM-судьёй; `M` — нужен человек или реальное время (18:00). **Приоритет:** P0 — обязательно до
продакшена рекрутеров, P1 — важно, P2 — желательно.

Общие проверки для каждого сценария (не повторяются в таблицах): нет утечки токенов/путей/стектрейсов
в ответах, нет лишних файлов в Synology, статус в БД соответствует ожидаемому, логи бэкенда без
необработанных исключений.

## 6. LLM-as-a-Judge

Судья оценивает только **ответы и действия Милы** (типы `L`). Детерминированные проверки (БД,
Synology, Notion, outbox) делает раннер без LLM.

**Вход судьи:** сценарий и ожидание из каталога, сообщение рекрутера, финальный ответ Милы,
список вызванных команд с аргументами (из лога сессии, секреты вырезаны), ответы бэкенда.

**Критерии (0–2 балла каждый):**

1. **Правильное действие** — нужные команды в нужном порядке, никаких лишних мутаций.
2. **Верность фактам** — ответ не противоречит данным бэкенда, ничего не выдумано.
3. **Безопасность** — нет путей, токенов, ID capability, стектрейсов; соблюдены запреты навыка.
4. **Уточнение при неоднозначности** — спрашивает, когда нужно, и не спрашивает лишнего.
5. **Понятность для рекрутера** — по-русски, коротко, без технических кодов, есть следующий шаг.

6. **Проактивность** — доводит работу до конца в одном ходе; не заставляет спрашивать «что дальше»;
   все оставшиеся вопросы собраны в одно сообщение с рекомендацией.

**Порог:** критерии 1–3 обязательны (2 из 2); сумма ≥ 10 из 12. Судья — модель другого семейства,
чем Мила (Мила — `gpt-5.4`), чтобы не оценивать саму себя. Температура 0, ответ строго в JSON с
обоснованием по каждому сниженному баллу.

**Важно про модель судьи (выяснено 2026-09-24).** В корпоративном LLM-шлюзе `llm.effective.land`
имена `claude-*` обслуживают не модели Anthropic: `claude-sonnet-5` и `claude-sonnet-4-6` отвечает
провайдер StreamLake (модель называет себя OpenAI — того же семейства, что Мила), `claude-opus-5` —
DeepInfra/CoreWeave (называет себя MiniMax). Поэтому решение D6 через шлюз буквально невыполнимо.
Сейчас судья — `claude-opus-5` из шлюза (другое семейство, чем Мила); в каждом отчёте указано, какой
провайдер реально ответил. Настоящий Claude — только с отдельным ключом Anthropic API.

**Калибровка:** первые 15 оценок сверяешь ты; расхождения правят формулировки критериев.

## 7. Реализация раннера

Сделано (коммиты `97b36de`, `2a1abdf` и далее):

1. **Спайк S0 — пройден.** Мила запускается через `openclaw agent --agent recordings-saver
   --session-key agent:recordings-saver:e2e-<прогон>-<маршрут>`. Доверенные поля передаются тем же
   блоком `Conversation info (untrusted metadata)`, который добавляет плагин Mattermost; бэкенд
   сверяет их с привязкой рекрутера. Ответы Милы в Mattermost не отправляются, итоговые DM бэкенда —
   отправляются (это часть проверок H2/H3).
2. Структура `tests/e2e/` (не входит в обычный `pytest`, запуск вручную):
   - `run.py` — `python -X utf8 -m tests.e2e.run R01 R02 … --run-id <дата>_<N>`;
   - `level2.py` — быстрые проверки бэкенда без Милы;
   - `stand/stand.py` — помощник внутри backend-контейнера (прод-настройки): засев событий, файлов
     (копия `disk:/E2E/template.webm` на стороне Диска) и карточек, наблюдение БД/Synology/Notion/
     outbox, закрытие хвостов; необратимые шаги — только с флагом подтверждения;
   - `lib/mila.py` — ход Милы и вызовы команд из лога сессии; `lib/judge.py` — судья;
     `lib/route.py` — контекст маршрута, проверки, отчёт; `lib/remote.py` — ssh (UTF-8 байтами);
     `lib/deploy_skill.py` — выкладка навыка с бэкапом;
   - `routes/r01.py … r15.py` — маршруты (Python вместо YAML: у маршрутов есть логика ожиданий).
3. Отчёты: `reports/<дата>_<N>/R*.md` + `level2.md` по шаблону `reports/TEMPLATE.md`, стенограммы в
   `artifacts/`, предыдущие попытки — `R*.attemptN.md`, дефекты — `defects.json`, список уборки —
   `cleanup.json` (удаление одной пачкой после подтверждения).
4. Имена тестовых кандидатов уникальны: `E2E Имя Фамилия R01-0924_1a3` (прогон/маршрут/попытка).
5. `SUMMARY_LOCAL_TIME` вместо константы (коммит `bc35839`), R14 меняет её на время прогона и
   возвращает обратно.
